## 1. Проблема: захардкоженный id

```yaml
# ❌ было
run: curl -f http://127.0.0.1:8080/app/task/1
```

Тест работал только потому, что база в CI **всегда новая** и первая задача получает id `1`. Если в базе уже есть данные или последовательность id сдвинулась, тест проверяет чужую задачу или падает без причины.

> [!important] Правило
> Тест должен работать с тем, **что сам создал**, а не надеяться на конкретные значения.

```yaml
# ✅ стало
- name: Create task
  run: |
    response=$(curl -f --retry 10 --retry-connrefused --retry-delay 2 \
      -X POST http://127.0.0.1:8080/app/task \
      -H "Content-Type: application/json" \
      -d '{"name":"ci_test","status":"new"}')
    echo "$response"
    echo "TASK_ID=$(echo "$response" | jq -r '.id')" >> "$GITHUB_ENV"

- name: Get task by id
  run: curl -f http://127.0.0.1:8080/app/task/$TASK_ID
```

### Разбор по кусочкам

| Кусок | Что делает |
|---|---|
| `response=$(curl ...)` | выполнить curl, **вывод** (тело ответа) положить в переменную |
| `echo "$response"` | показать ответ в логе CI (для отладки) |
| `echo "$response" \| jq -r '.id'` | передать JSON в `jq`, достать поле `id` |
| `-r` у jq | raw: вывести `7`, а не `"7"` (без кавычек JSON) |
| `>> "$GITHUB_ENV"` | дописать `TASK_ID=7` в специальный файл раннера |

## 2. `$(...)` — подстановка команды

```bash
today=$(date +%F)        # выполнить date, результат → в переменную
echo "$today"            # 2026-10-07
```

- `$(команда)` → bash **выполняет** команду и подставляет её **вывод** (stdout).
- Пробелов вокруг `=` быть **не должно**: `x = 1` bash поймёт как команду `x` с аргументами.
- Можно вкладывать: `echo "id=$(echo "$r" | jq -r '.id')"`.

> [!tip] Не путать
> - `$(...)` — вывод команды
> - `${VAR}` — значение переменной
> - `$?` — **код выхода** последней команды (а не вывод)

## 3. `$GITHUB_ENV` — передача переменных между шагами

> [!important] Главное
> Каждый шаг (`run:`) — это **отдельный процесс bash**. Переменная, созданная в одном шаге, в следующем **не существует**. Чтобы передать значение дальше, его пишут в файл, путь к которому лежит в `$GITHUB_ENV`.

### Как это работает

1. **Перед каждым шагом** раннер сам создаёт переменную `GITHUB_ENV`. В ней лежит **путь к файлу**, а не значение:
   ```
   /home/runner/work/_temp/_runner_file_commands/set_env_3f9a...
   ```
2. Мы **дописываем** в этот файл строку `ИМЯ=значение`.
3. Шаг завершается → раннер **читает файл** → добавляет переменные в окружение **всех следующих** шагов.

```
шаг "Create task"                         раннер                   шаг "Get task by id"
echo "TASK_ID=7" >> "$GITHUB_ENV"  ──▶  читает файл после шага  ──▶  $TASK_ID = 7
```

### Важные детали

| Деталь | Почему |
|---|---|
| `>>`, а не `>` | `>>` **дописывает**, `>` **перезаписывает** файл и стирает строки, которые туда уже положили другие |
| В **том же** шаге `$TASK_ID` пустой | раннер читает файл только **после** окончания шага |
| `"$GITHUB_ENV"` в кавычках | это путь; без кавычек сломается, если в нём будут пробелы |
| `$GITHUB_ENV` мы **не создавали** | его заранее задаёт раннер |

> [!example] Проверить своими глазами
> ```yaml
> - name: Debug
>   run: |
>     echo "Путь: $GITHUB_ENV"
>     echo "TASK_ID: $TASK_ID"
> ```

> [!info] Родственники
> - `$GITHUB_OUTPUT` — выходные значения шага (`steps.<id>.outputs.<имя>`)
> - `$GITHUB_STEP_SUMMARY` — markdown-отчёт на странице запуска
> - В GitLab CI похожее: `artifacts: reports: dotenv: build.env`

## 4. Три похожие вещи, которые легко спутать

| Что | Где живёт | Кто создаёт | Зачем |
|---|---|---|---|
| `.env` | **файл** в папке проекта | ты (локально) / шаг `Create .env` (в CI) | значения для `${...}` в docker-compose.yml |
| `ENV_FILE` | **секрет** в настройках репозитория GitHub | ты, один раз, через Settings → Secrets | хранит содержимое `.env` для CI |
| `$GITHUB_ENV` | **файл раннера**, путь в переменной | раннер GitHub | передать переменные между шагами |

## 5. Путь секрета: от GitHub до Postgres

База **ничего не знает** про GitHub. Она видит только переменные окружения своего контейнера.

```
GitHub secret ENV_FILE
   │ ① env: ENV_FILE: ${{ secrets.ENV_FILE }}
   ▼
$ENV_FILE — переменная окружения шага "Create .env"
   │ ② printf '%s\n' "$ENV_FILE" > .env
   ▼
файл .env на раннере
   │ ③ docker compose читает .env автоматически
   ▼
${POSTGRES_USER} в docker-compose.yml → подставлено значение
   │ ④ environment: у сервиса db
   ▼
POSTGRES_USER=... внутри контейнера → entrypoint postgres создаёт пользователя и БД
```

> [!warning] Только при первом запуске
> Образ `postgres` читает `POSTGRES_*` только когда volume **пустой**. В CI это не проблема: каждый раз чистая виртуалка, а в конце `down -v`.

## 6. Шаг `Create .env` построчно

```bash
if [ -z "$ENV_FILE" ]; then                         # -z: строка пустая?
  echo "::error::Secret ENV_FILE is empty or missing"  # ::error:: — красная аннотация в интерфейсе GitHub
  exit 1                                            # код ≠ 0 → шаг красный
fi
printf '%s\n' "$ENV_FILE" > .env                    # записать секрет в файл
```

- **Fail fast:** если секрета нет, падаем **сразу** с понятным текстом, а не через 2 минуты с `password authentication failed`.
- `::error::` — это **workflow command**: специальная строка в выводе, которую GitHub понимает как команду.

### `printf '%s\n'`: формат и аргумент

```bash
printf 'ФОРМАТ' аргумент1 аргумент2 ...
printf '%s\n' "$ENV_FILE"
#       │       └── аргумент: что печатаем
#       └── формат: %s = «вставь сюда строку», \n = перевод строки
```

> [!danger] Почему не `printf "$ENV_FILE"`
> Тогда содержимое станет **форматом**. Если в пароле есть `%`, printf попытается его интерпретировать и испортит значение. Данные всегда передаём **аргументом**.

Почему не `echo`: поведение `echo` с `-e`, `-n` и `\` отличается в разных shell. `printf` предсказуем.

### Переменная — это одна строка с переводами строк

Секрет `ENV_FILE` хранит три строки `.env`, но для bash это **одна** строка, внутри которой есть символы `\n`. В кавычках `"$ENV_FILE"` она передаётся целиком, и переводы строк сохраняются.

## 7. Кавычки и word splitting

> [!important] Правило
> **Всегда** пиши переменные в двойных кавычках: `"$VAR"`.

```bash
name="my file.txt"
touch $name       # ❌ создаст ДВА файла: my и file.txt
touch "$name"     # ✅ один файл: my file.txt
```

Без кавычек bash делает **word splitting**: режет значение по пробелам, табам и переводам строк, а потом ещё раскрывает `*` (globbing).

| Кавычки | Что делают |
|---|---|
| `"..."` | переменные раскрываются, но значение **не режется** |
| `'...'` | всё **как есть**, `$` не раскрывается |
| без кавычек | раскрытие + разрезание + `*` |

```bash
echo "$HOME"   # /home/runner
echo '$HOME'   # $HOME
```

## 8. YAML: дублирующиеся ключи

```yaml
# ❌ невалидно: два ключа run в одном шаге
- name: Create task
  run: curl ...
  run: echo ...
```

Шаг — это **словарь**, в словаре ключи уникальны. Несколько команд пишут в **один** `run: |`.

## 9. Healthcheck: параметры

```yaml
healthcheck:
  test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"]
  interval: 5s       # запускать проверку каждые 5 с
  timeout: 3s        # не ответила за 3 с → провал
  retries: 10        # 10 провалов ПОДРЯД → unhealthy
  start_period: 5s   # первые 5 с провалы не считаются; первый успех → сразу healthy
```

- Худший случай до `unhealthy`: ≈ 5 + 10 × 5 ≈ 55 с.
- `urlopen` бросает исключение на 4xx/5xx и при ошибке соединения → Python выходит с кодом 1 → провал.
- Docker **сам не перезапускает** unhealthy-контейнер. Статус используют `depends_on: service_healthy` и `up --wait`.

### То же в Kubernetes

| Docker | Kubernetes probe |
|---|---|
| `interval` | `periodSeconds` |
| `timeout` | `timeoutSeconds` |
| `retries` | `failureThreshold` |
| `start_period` | `initialDelaySeconds` / `startupProbe` |

| Probe | Что делает при провале |
|---|---|
| `livenessProbe` | **перезапускает** контейнер |
| `readinessProbe` | **убирает под из трафика** (из Service), не перезапуская |
| `startupProbe` | пока не прошла, две другие не запускаются (для медленного старта) |
