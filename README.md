# FastAPI + PostgreSQL в Docker: CI, healthchecks, бэкапы

Учебный DevOps-проект. Простой REST API для задач (FastAPI) с базой PostgreSQL. Упор не на код приложения, а на то, что вокруг него: контейнеризация, проверка здоровья сервисов, CI с реальными API-тестами, работа с секретами, автоматические бэкапы с проверкой восстановления.

## Стек

- **Приложение:** Python 3.12, FastAPI, psycopg 3
- **База:** PostgreSQL 17
- **Инфраструктура:** Docker, Docker Compose
- **CI:** GitHub Actions
- **Скрипты:** Bash, cron

## Архитектура

```
            :8080
  клиент ─────────► app (FastAPI, uvicorn :8000)
                        │  DB_HOST=db (DNS внутри docker-сети)
                        ▼
                    db (postgres:17) ── volume pg_data
```

- Оба сервиса в отдельной bridge-сети `app_network`. Порт базы наружу **не открыт**, к ней ходит только приложение.
- **Healthchecks:** `db` через `pg_isready`, `app` через эндпоинт `/health`, который делает `SELECT 1` в базу.
- `app` стартует только после того, как `db` стала healthy (`depends_on: condition: service_healthy`).
- Данные базы хранятся в именованном volume `pg_data` и переживают пересоздание контейнеров.

## Запуск

```bash
cp .env.example .env        # вписать свои значения
docker compose up -d --build --wait
```

`--wait` ждёт, пока оба сервиса станут healthy. Документация API (Swagger): http://localhost:8080/docs

## API

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/health` | проверка приложения и связи с БД (503, если база недоступна) |
| POST | `/app/task` | создать задачу `{"name": "...", "status": "..."}` |
| GET | `/app/tasks` | все задачи |
| GET | `/app/task/{id}` | задача по id (404, если нет) |
| DELETE | `/app/task/{id}` | удалить задачу (404, если нет) |

## Секреты

- Пароли и имена хранятся в `.env`, файл в `.gitignore`. В репозитории лежит только шаблон `.env.example`.
- В CI `.env` собирается из секрета репозитория `ENV_FILE`. Если секрет пустой, пайплайн падает сразу с понятной ошибкой.

## CI (GitHub Actions)

[`.github/workflows/tests.yml`](.github/workflows/tests.yml) на каждый push:

1. Собирает `.env` из секрета.
2. Поднимает стек `docker compose up --build --wait`.
3. Прогоняет API-тесты через `curl`: создание задачи, затем получение, удаление и проверка, что удалённая задача отдаёт 404. Id созданной задачи передаётся между шагами через `$GITHUB_ENV`, без захардкоженных значений.
4. При падении выводит логи контейнеров.
5. Всегда убирает за собой (`docker compose down -v`).

## Бэкапы

Три Bash-скрипта, все с `set -euo pipefail` и понятными ошибками в stderr.

| Скрипт | Что делает |
|---|---|
| [`backup.sh`](backup.sh) | проверяет, что контейнер БД запущен, затем `pg_dump` → `backups/pg_data_backup_<дата>.sql.gz` |
| [`verify_backup.sh`](verify_backup.sh) | поднимает **временный** контейнер `postgres:17`, ждёт готовности (с таймаутом), восстанавливает последний бэкап, проверяет, что данные на месте (`count(*) > 0`). Контейнер удаляется при любом исходе (`trap cleanup EXIT`) |
| [`nightly_backup.sh`](nightly_backup.sh) | обёртка: бэкап → проверка → удаление бэкапов старше 7 дней. Старые бэкапы удаляются **только после** успешной проверки нового |

Бэкап, который не проверяли восстановлением, считается непроверенным. Поэтому восстановление проверяется каждую ночь и на отдельном контейнере, а рабочая база не затрагивается.

Запуск по расписанию (crontab), каждый день в 04:05:

```
5 4 * * * /path/to/project/nightly_backup.sh >> /path/to/project/logs/nightly_backup.log 2>&1
```
